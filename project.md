# Project brief

## Identity

- **Name:** ResearchOps — Evidence-Grounded Technical Research Agent
- **Product:** A technical research engine that turns a question into a concise, evidence-backed answer with inspectable citations, plus an optional professional PDF report.
- **Audience:** Engineers, technical leaders, and researchers comparing tools, systems, and implementation choices.

## What it should do

1. Accept a research question and keep its scope clear.
2. Plan targeted subqueries and a bounded research budget.
3. Search the web with Tavily, fetch pages with HTTPX, and extract readable content with Trafilatura.
4. Rank sources, extract structured evidence, and verify claims as supported, conflicting, partially supported, or unsupported.
5. Return a useful answer in the UI with citations that point to the supporting sources.
6. Generate a PDF only after the user selects **Generate Report**.

The answer should distinguish evidence from inference, explain meaningful conflicts, and avoid presenting unsupported claims as facts.

## Report behavior

The model can propose the report title, topic wording, section content, executive summary, tables, and recommendations from the research result. ReportLab Platypus owns layout and pagination. A fixed visual system uses a white page, pink and sky-blue accents, professional typography, consistent spacing, headers, footers, and page numbers.

Default section order:

1. Title
2. Executive Summary
3. Key Findings
4. Comparison Tables
5. Detailed Analysis
6. Recommendation
7. Sources

Tables and paragraphs must flow across pages cleanly, with no clipped content or overlaps. The model supplies content; templates enforce visual consistency.

## Architecture

```text
React + Tailwind → FastAPI / Pydantic → LangGraph stateful workflow
                                      ├─ planner and scope guard
                                      ├─ Tavily search
                                      ├─ HTTPX fetch + Trafilatura extraction
                                      ├─ evidence extraction and source ranking
                                      ├─ claim verification and conflict routing
                                      └─ synthesis → cited web answer
                                                  └─ explicit request → ReportLab PDF

OpenAI / Gemini / Nebius → model provider layer
LangSmith                 → tracing and evaluation
```

Keep external actions in service/tool functions and reasoning or transformations in graph nodes. Pydantic models define validated boundaries for requests, evidence, verification results, and answers.

## Selected technology

| Capability | Choice |
|---|---|
| Frontend | React + Tailwind CSS |
| Backend and validation | FastAPI + Pydantic |
| Model APIs | OpenAI + Gemini + Nebius |
| Agent workflow | LangGraph + LangChain |
| Web search | Tavily |
| Page retrieval and cleanup | HTTPX + Trafilatura |
| Observability | LangSmith |
| PDF reports | ReportLab Platypus |

## Product constraints

- No PDF is generated by default.
- No simulated research steps, source counts, timings, or model availability in the UI.
- Citations must resolve to sources actually used by the workflow.
- Provider secrets belong in environment configuration and must not be committed.
- Research resource ceilings are centralized in validated settings and configurable through `.env`: searches, sources, pages, iterations, token budget, and runtime.
- Keep the initial repository structure short; introduce modules as implementation needs them.
